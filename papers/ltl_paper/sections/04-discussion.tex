\section{Discussion} \label{sec:discussion}

Encoding functional intent as temporal properties moves requirements from informal statements into a checkable language aligned with open-system boundary practice \citep{salado2019mbse,BaierKatoen2008}. The assertional reading developed here is a reinterpretation of the Functionality Cotyledon for verification workflow, not a replacement of T3SD when a reference system and homomorphism already exist and remain convenient.

\subsection{Relationship to Classical Functionality Cotyledon}
\label{sec:classical-fc}

On the dynamics-encoding bridge fragment, for fixed $Z_{\text{spec}}$,
\[
  Z_{\text{impl}} \in \mathrm{FC}_{\text{constructive}}(Z_{\text{spec}})
  \;\;\Longleftrightarrow\;\;
  Z_{\text{impl}} \models_{\mathrm{dyn}} \Phi_{Z_{\text{spec}}},
\]
where $\mathrm{FC}_{\text{constructive}}(Z_{\text{spec}})$ is the set of buildable systems that admit a Wymore system homomorphism into $Z_{\text{spec}}$ (Appendix~\ref{app:hom-biimp}; Section~\ref{sec:case-study}). The property sets exhibited for the ones-counter, string recognizer, and real accumulator are instances of Table~\ref{tab:phi-dyn-fragment}.

Formulas outside the dynamics-encoding fragment do not, in general, imply existence of such an $h$. As a concrete contrast: $F(\mathit{output}(1))$ may hold of a buildable system that eventually pulses an accept bit without agreeing with a given reference transition table, and a bare input/output safety property may be shared by systems with different next-state functions. Those cases lie outside the bi-implication; the bridge requires a complete $\Phi_{\mathrm{dyn}}$ (compiled from $Z_{\text{spec}}$, or authored in the same schemas).

Global set equality between constructive FC and assertional FC for arbitrary $\Phi$ outside the fragment remains open. Output-table-only encodings and $F$ formulas conflated with dynamics tables are outside the bi-implication.

\subsection{Expressivity, Checking, and Decidability}
\label{sec:expressivity}
\label{sec:limitations}

Restricting to $\Phi_{\mathrm{dyn}}$ buys the homomorphism bi-implication; it also limits what engineers can \emph{say}. The fragment admits only table-shaped $G$/$X$ clauses compiled from a reference $\delta$ and $\rho$ (Table~\ref{tab:phi-dyn-fragment}): no $F$, no $U$, and no free-form quantification over values beyond indexing those clauses. Richer dialects---propositional LTL with the full operator set, or FO-LTL over infinite or real coordinates---let engineers author desired behavior beyond that fragment, at the cost of leaving the strict T3SD implementability bridge.

Two concrete contrasts from the case studies make the gap vivid. For the string recognizer, $\Phi_{Z_{01110}}$ requires every guided step of the reference automaton. In FO-LTL one can instead write
\[
  F\bigl(\mathit{output}(1)\bigr)
\]
(``eventually emit an accept pulse''). That formula is easy to author as a boundary requirement, but it does not constrain \emph{which} path produced the pulse: a buildable that accepts for the wrong reason still satisfies it, and satisfaction is not equivalent to a Wymore homomorphism into $Z_{01110}$. For the real accumulator, FO-LTL can state a threshold liveness that $\Phi_{\mathrm{dyn}}$ cannot express at all without changing the reference system itself:
\[
  F\bigl(\exists\, s\in\mathbb{R}.\; \mathit{state}(s)\wedge |s|\ge\theta\bigr)
\]
(``the running sum eventually reaches threshold $\theta$''). The dynamics-encoding fragment has no $F$ and only next-state/readout schemas; ``eventually exceed $\theta$'' is not a row of any fixed transition table. Response patterns such as $G\bigl(\mathit{cmd}\rightarrow F(\mathit{done})\bigr)$ and until-formulas such as $(\neg\mathrm{alarm})\,U\,(|s|\ge\theta)$ likewise lie outside $\Phi_{\mathrm{dyn}}$.

The engineering tradeoff is therefore deliberate. Use $\Phi_{\mathrm{dyn}}$ when the question is classical implementability of a stated $Z_{\text{spec}}$. Use a more expressive fragment when the question is whether a buildable meets authored boundary intent---accepting that the answer no longer coincides with existence of a homomorphism.

The bi-implication itself is a \emph{semantic} equivalence. It does not imply that checking $Z_{\text{impl}} \models_{\mathrm{dyn}} \Phi_{Z_{\text{spec}}}$ is decidable for arbitrary systems. On finite state, input, and output spaces, propositional encodings of the fragment admit standard finite-state decision procedures. For infinite discrete state or real-valued coordinates, FO satisfaction is not decidable in general \citep{BaierKatoen2008}; practical constraints include finite abstraction, bounded-horizon unrolling, restricted input classes, and theory-specific queries (for example, linear real arithmetic on a fixed finite unrolling). Automatic discovery of homomorphism maps on infinite or real state is not claimed; on the finite recognizer, maps may be exhibited and verified (Section~\ref{sec:case-pattern}).

Relative to classical hand-maintained homomorphisms, the case studies illustrate maintenance across a system's lifecycle: a single compiled $\Phi_{\mathrm{dyn}}$ is re-checked against prototype (v1), instrumented (v2), and refactored (v3) buildable systems, while the classical approach requires a structure-specific witness at each iteration. The string recognizer's shift-register v3 is the structural-divergence exhibit: $h_S$ is no longer a component projection. That is a workflow contrast under the bi-implication, not a claim that map discovery is automatic or that property checking is always cheaper. The evidence is qualitative, not a timed benchmark.

\begin{itemize}
    \item \textbf{Open:} global FC equality for arbitrary $\Phi$ outside the fragment.
    \item \textbf{Not claimed:} automatic homomorphism search on infinite or real state; continuous-time hybrid verification; identification of floating-point with $\mathbb{R}$.
    \item \textbf{Future work:} SysML tooling integration; broader empirical comparison of verification effort; deeper related-work engagement with runtime verification and supervisory control.
\end{itemize}
